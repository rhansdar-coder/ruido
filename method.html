Methodology

Every number Ruido publishes is reproducible from a public RPC endpoint with no API key, no indexer subscription, and no dependency tree. If you cannot reproduce it, it is not a measurement.

1. Index the pool

We call starknet_getEvents against the pool address from block 0 to latest, following continuation tokens until the RPC stops returning one. No sampling, no window, no "recent activity" shortcut: a set measured over a partial history is a set measured over a different pool.

Event names are derived from the deployed class ABI, never from a hardcoded table. Two reasons. The on-chain version of a pool diverges from the version in the repository that documents it, and pools get upgraded. Both were true for the pool we measured: it has run three distinct implementations, and a single-ABI index silently drops the events emitted before the last upgrade.

We resolve this by discovering classes lazily. When an event key cannot be explained by any ABI we have loaded, we fetch the class hash that was live at that block and merge its layout in. When no unexplained keys remain, no event has been dropped — and we report the class history alongside the data, so the completeness claim can be checked.

One thing that history is not is a count of implementations. Lazy discovery only looks when an event key is unexplained, so an upgrade whose event layouts happen to be covered leaves no trace. Sepolia has run three implementations; the corpus lists two. Probing starknet_getClassHashAt directly at each era is what settles it, and it also shows the same class hash (0x30b8c540…) live on Sepolia and mainnet — so a class hash does not identify a network. Treat classHistory as a lower bound, which is why the completeness claim above is about events rather than about classes. 

npm run corpus           # index -> data/corpus.json
npm run corpus:mainnet   # same, against mainnet

2. Reduce to what an adversary sees

The index keeps block numbers and transaction hashes. Nothing else. That is deliberate and it is also a limitation worth stating plainly: the adversary modelled here is weaker than a real one. They do not see a mempool, IP addresses, exchange withdrawal records, or the amounts behind a deposit. Every figure is therefore an upper bound on privacy.

Notes versus origins

A transaction can mint many notes. When it does, all of those notes share an origin, and a shared origin is not a probabilistic inference — it is written into the ledger. One account, one nonce, one transaction.

This distinction decides whether a measurement is honest. The pool we measured has a single transaction that minted 295 notes in one block. Counting notes, that is 295 anonymous people. Counting origins, it is one. Every table Ruido publishes carries both columns, and they are never averaged together.

The adversary models

3. Define the number

Bits is log2 of the candidate count. It is the right unit because it is the unit an adversary pays in: each additional bit doubles the work, and each additional bit of cover doubles the cost of buying it.

One candidate is zero bits. There is no hiding inside a set of one, and a table that reports "1 candidate, 0 bits" is reporting a complete leak, not a small number.

We report the mean over a sample of real notes, not over a single note. Under a tight timing window a single note's candidate count is 1 or 2 and moves non-monotonically as cover is added, which would let a scaling curve claim that more cover buys less privacy. Averaging over a sample is what turns the count into a curve that can be read. The median is reported beside it, because the mean of a set containing single-note transactions is a different quantity than the median, and both are true.

The denomination axis is partial, and that is measured too

An amount is public for a note in exactly two ways. An open note publishes a note_id and OpenNoteDeposited publishes the same note_id with an amount; or the note's transaction carries exactly one distinct Deposit. A change note minted by spending an existing note has neither, so its amount is unobservable. That is not a limitation of our tooling, it is a property of the ledger, and it means the axis covers 34.3% of Sepolia notes and 55.3% on mainnet.

So the axis is reported over the subset it can see and never extrapolated to the pool. Where it applies, it is the sharpest axis measured: a ±1-block observation falls from 64.93 candidates to 1.27, and 89.5% of amount-visible notes have no other note of their denomination in that window.

One candidate source was checked and rejected rather than assumed. EncNoteCreated carries a packed_value felt, and if the amount were in it the axis would cover every note. Its magnitude sits 55 orders of magnitude above the amounts it would have to encode, so it is a commitment. npm run check:packed reproduces that.

A wrong amount is not an error, it is a smaller anonymity set. The first version of this join broadcast one event's amount onto every note in its transaction, which gave 508 notes an amount they should not have and inflated coverage from 34.3% to 40.4%. Nothing about the resulting numbers looked wrong — a smaller candidate set reads as a better finding. Only Deposit is evidence about an encrypted note; open-note amounts are matched to their own note by note_id. A regression test fails if the two are merged again.

The unit is seconds, not blocks

A window expressed in blocks is expressed in a unit whose meaning changes from chain to chain. Robinhood Chain produces a block every 0.102 s, Base every 2.000 s, Starknet every 1.702 s, and Ethereum every 12.056 s. So "the adversary knows the block to within 10" is 1.0 second on one and 120.6 seconds on another, and a table placing those two columns side by side compares nothing at all.

This report originally stated its windows in blocks. That was defensible only for as long as every chain in the table shared a block time, and it stopped being true the moment a second chain entered. Every window is now stated in wall-clock seconds, and the conversion is measured from the chains rather than assumed:

The extremes differ by a factor of 118×, and the correction runs in both directions. The published STRK20 window of ±10 blocks is ±17.0 s; on Robinhood Chain that is ±167 blocks, and on Ethereum it is ±1 block — which is why Ethereum's ±1 s and ±10 s rows are identical, ten seconds being less than one block. Reproduce with npm run blocktimes.

4. Separate user traffic from load generation

Testnet pools carry scripted traffic that mints hundreds of notes per transaction. It is not anonymous activity and it should not be counted as such, but it is also not removable: it is on the chain, the adversary sees it, and it does provide cover.

So we report both. The whole-pool table includes it. A second table restricts to human-scale transactions — at most six notes, which is above the five-note shape of the wire protocol we studied — and reports the same models over that subset. Neither table is presented alone.

5. What would falsify this

Concretely, and in order of how much they would change the conclusion:

  • Indexing mainnet, where volumes are lower and the measurement should get worse. Falsified. Mainnet reads 1.76 bits against Sepolia's 0.15 — better, not worse, because mainnet is 4.6× denser rather than quieter. The prediction is struck through, not deleted, because the falsification is the result.
  • Adding the denomination axis. It can only shrink candidate sets, never grow them, so it cannot rescue any figure above. Done, and it did not rescue anything — it confirmed the direction and sharpened it. The indexer now decodes amounts out of the event payloads. On the 34.3% of Sepolia notes whose amount is publicly derivable, a ±1-block observation falls from 64.93 candidates to 1.27. Getting there required fixing a join bug that had been silently inflating coverage by 508 notes, which is the more instructive half of the result: a wrong amount is not an error, it is a smaller anonymity set, and a smaller anonymity set looks like a better finding.
  • Showing that the ±17 s window is unjustified — that a real adversary cannot in fact narrow to a range that tight. Our 98.3% at ±1 block on Sepolia is the case to argue with.
  • Showing that a large timing candidate set on a chain with persistent, cleartext addresses does provide anonymity. That is the claim section 6 rests on, and it is the one most worth attacking.
  • Finding a transaction on any of the three chains whose sender is not present in the public block data. That would falsify the 0-bit result directly.
  • Finding a contract that passes all four pool conditions. That would be a candidate and would need its own measurement; the 0-bit figure covers the transparent population only.
  • Showing that a defender can place cover at the pool's fee without paying the fee. That would break the sybil resistance the cover market depends on.

This is not a claim that the pool is broken. It does what it says: it hides what a note is worth and who spends it. It does not hide when the note was created, because creation is an on-chain event. At 1.25 notes per thousand blocks, "when" is very nearly a unique identifier. That is the finding, and it is a property of the traffic, not a defect in the cryptography.

6. Chains with no shielded pool

A meter that only ever points at the thing its author likes is not a meter. So we pointed it at three chains that are not STRK20 — Robinhood Chain (Arbitrum Orbit, 4663), Base (OP Stack, 8453) and Ethereum (1) — none of which has a shielding primitive. Adding a chain is a data change, not a code change: they live in src/chains.mjs, and a test asserts the indexer contains no hardcoded addresses or chain IDs.

The question this report is built around, "how many other notes could this be", has no answer there, because there are no notes. The sender is written in the transaction. So the measurement reports what can be measured and names what cannot:

  • The timing axis, which exists on every chain, expressed in the same seconds as the STRK20 windows above.
  • Address reuse, because a second transaction from an address is not a new suspect — it is a confirmation of a link the adversary already held.
  • Contract concentration, because "what is this address doing" is largely answered by which contract it calls.
  • A behavioural test for a shielded pool, described below.

Why a big candidate set is not privacy

At ±17 s, all three chains have a much larger candidate set than STRK20 mainnet does at the same window — 2,304 senders, 1,356 and 688, against 3.25 notes. All three have an effective anonymity of 0 bits, and both statements are true simultaneously, because a candidate set is only an anonymity set when the parties inside it are indistinguishable from each other. On STRK20 they are unlinkable notes. Here they are persistent addresses, and an address that persists is a name.

Ethereum is also where the seconds correction runs backwards. Its block time is 12.056 s, so ±17 s is ±1 block, and the ±1 s and ±10 s rows of its timing table are identical — widening the window by ten seconds widens it by nothing, because ten seconds is less than one block. A block-denominated table across these chains would have hidden that.

Testing for a pool without trusting a label

Contract names were not resolved against an explorer. An explorer is a third party with its own incentives, and its label is not evidence. We tested behaviour instead: a mixer concentrates transfers into a handful of fixed denominations reused hundreds of times, which leaves a small value space relative to the number of transfers. Ordinary traffic does the opposite.

That test was wrong three times before it was right, and each correction came from running it:

  1. Whole-chain was the wrong granularity. On Ethereum it reported "no pool" while Tornado Cash was deployed there. A 10-hour window carries 340,000 value transfers, and a mixer with a hundred deposits is 0.03% of that, so a chain-wide distribution can never be concentrated enough to fire. A mixer is a contract, not a chain.
  2. The value shape over-reports. Per contract on Robinhood Chain it fired on eleven contracts, every one a fixed-amount payment pattern: a sale at a fixed price, a batch payer, one bot repeating an amount. The deposit shape cannot tell those from a pool, so two conditions were added — more than one depositor, and value flowing both ways.
  3. A fee collector wears the same shape. One candidate survived both: 120 deposits of exactly 0.0005 ETH from 72 addresses. Its withdrawals settled it — seven of ten went to the same address in irregular lumps of 0.77 to 18.62 ETH. A pool returns the denominations it took; this swept a balance to a treasury. Hence a third condition: the outflow must be pool-shaped too.

A detection therefore requires four things, of which the last three are requirements a pool cannot fail rather than tuned thresholds. Every contract the shape test fired on is listed with the reason it was rejected — on all three chains the viable count is zero, and the gap between the two counts is the finding.

One further honesty note. Ethereum was registered as the positive control for this detector, because Tornado Cash is deployed there. Then it was measured, and the control does not work: in the observed window the 0.1 ETH pool received one transfer. Tornado Cash is deployed and effectively dormant, so a recent window cannot exercise the detector at all. The proof that it can fire is a unit test with a mixer-shaped fixture, not this chain.

Exclusions are stated, not applied quietly. The address 0x…a4b05 is written exactly once per block on Robinhood Chain; it is Arbitrum's L1-block-number pseudo-address, not a person, and left in the identity counts it becomes the single most active account on the chain. Base has the equivalent in 0xdeaddead…0001, the OP Stack L1 attributes depositor. Both are excluded and reported separately.

What is not excluded is the list of addresses transacting close to once per block. Base has 23 of them and Ethereum 10, and every one is a high-frequency bot rather than infrastructure. A count-based rule that dropped them would have deleted 23 real participants from Base's figures and flattered every number built on them. They are reported instead.

Separately, every measurement is a sampled window, not a census. The public RPC sustains roughly 20 blocks per second with batching, and these chains are tens of millions of blocks — weeks to years of scanning. The window, its coverage, and the count of any blocks that could not be fetched are printed with the result. A sample that presents itself as a census is worse than no sample.

The indexer holds its window in memory, and Base is dense: a 12,000-block attempt died with a heap-limit crash after 6,125 blocks. It now prints free RAM and an estimated requirement before starting, and Base's window is 3,000 blocks for that measured reason.

Reproducing it

git clone <repo> && cd ruido
npm test                  # 360 tests, no dependencies
npm run blocktimes        # measure the chains' block times live
npm run corpus            # index the live STRK20 pool, decoding event payloads
npm run measure:corpus    # measure it, including the denomination axis
npm run verify:decode     # check the decoder against the live chain: 0 mismatches
npm run check:packed      # the negative finding about EncNoteCreated.packed_value
npm run rh:index          # index a window of Robinhood Chain
npm run rh:measure        # measure that window
npm run base:index        # index a window of Base
npm run base:measure
npm run eth:index         # index a window of Ethereum
npm run eth:measure
npm run measure           # the synthetic model, seeded
npm run quote             # price an order: bits, not decoys. Offline
npm run serve:provider    # a reference provider. Loopback by default; any other
                          # interface needs --token, and refuses to start without one
npm run serve:book        # the order book: it lists offers, never orders
npm run buy -- --provider http://127.0.0.1:8081 --cell 1.93 --bits 3 \
               --mode window --from 14865231 --denomination 10
npm run verify:journey    # measure -> order -> pay -> reveal, over real HTTP
npm run web               # view the dashboard

Requires Node 20 or later. Nothing else. The keccak implementation needed for Starknet selectors is in src/keccak.mjs, tested against vectors generated by an independent implementation.

Ruido is measurement software. It never holds funds and never touches a pool key. Nothing here is legal, financial, or investment advice.
